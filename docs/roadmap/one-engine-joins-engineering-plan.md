## 1. The owner's design

RRFlow is "one reasoning-data engine" (README), and rrflowDB, rrflowKV, rrflowQL, graph, lexical and vector "remain parts of that one system". The owner's own statements about it:

- **One query, the way SurrealDB or ArangoDB works, with Qdrant-grade vectors.** "It works like Surreal or Arango does when typing reasoning, Qdrant with a system that triggers all of them properly, hitting hot first and if necessary to cold" (2026-11-11). Gate J records the same: capabilities are "triggered properly, so that different reasoning can be chosen dynamically".
- **The engine owns the access paths, chosen by the reasoning need, not by cost.** The objective says the engine "turns authorized source revisions into retrievable records, source spans, semantic relationships and lexical/vector access paths", and that "a prompt retrieves current permitted evidence". Cost is a budget. It is not the goal.
- **rrflowLSM is the hot tier: an AI-optimized engine evolved from Fjall** (owner, 2026-11-11). **rrflowCLD is the cold tier: a custom, AI-optimized format that breaks from Parquet**, and becomes canonical once compaction moves data into it, so the LSM can reclaim space (owner decisions, 2026-11-11; F-06).
- **Knowledge paths default to cold**, but the engine can still reach them. Everything is tunable and evolvable, and nothing is hardcoded.
- **TurboQuant in all four parts:** persistent search, the inner-product variant, the model KV cache, and sync transfer ([quantization lifecycle](../reference/vector/quantization-lifecycle.md), OBJ-13).
- **Measured and tuned as one system** against SurrealDB, ArangoDB and Qdrant running beside it ([comparison lab](../../eval/lab/README.md)), on real hosts that also run other projects.

## 3. Target

1. **One statement.** rrflowQL carries relational filters, graph traversal, `MATCH` and vector similarity in one statement, with fusion as a plan operator whose method and constant are recorded. The research and its sources are in [section 6](#6-research). The request states the reasoning need: what evidence, which freshness (`AT VALID`/`KNOWN`), what quality (exact, or a recall target), and the budget.
2. **The engine chooses and reports.** The planner picks access paths to meet the stated quality within the budget, using estimated cardinality, and pushes filters into vector search. It never post-filters silently or falls back silently. `EXPLAIN` and every result report the chosen path, its rejected alternatives with reasons, and estimated against actual rows.
3. **The engine builds its paths.** The engine maintains scalar, BM25, adjacency, HNSW and TurboQuant paths, by declared policy, from the schema and the attunement evidence. Filterable fields come from the declared schema, and nothing waits for a client to ask.
4. **Hot first, cold if necessary, at one stamp.** A read at a stamp is served from the memtable, then the page cache, then segments. Below the cold watermark it falls through to rrflowCLD, using the same stamp and the same authentication. Each result reports which tier served it.
5. **Measured and tunable.** Each request carries one correlation id from HTTP through the engine, the store and the LSM, down to CLD, with time per layer. Every threshold is configuration bound into the estate's sealed configuration, and a lab run records its configuration digest and before/after diagnostics.

## 5. Owner decisions, 2026-11-11

1. **Read-audit durability is configurable and measured.** It is never fixed. The estate's sealed configuration chooses among:
   - a durable sync per read;
   - group-committed read audit;
   - durable read audit only when security is enforced.

   J1 must measure each mode's per-request cost, and J2 makes the setting and its measurement visible so it can be optimized. Security-on guarantees are tested in every mode that claims them.
2. **rrflowCLD format: the senior-engineering path for growth, scale and AI reasoning.** J8 first defines a versioned generation-format interface: one reader, a manifest that names each generation's format, and the stamp and authentication contract. CLD becomes canonical under that interface with the current Parquet generation, so the canonical move, reclaim and merged read are proven independently of the encoding. The custom AI-tailored format then arrives as a new generation format behind the same reader. It is designed from measured access patterns, such as which history and knowledge paths reasoning actually reads cold. Old generations stay readable until they are rewritten. The format is never chosen ahead of the measurements.
3. **The default request is tunable, never hardcoded, and tracked.** A plain request lets the engine choose its path against a configured quality default, initially recall 0.95 or exact where policy requires it. Every request records the default it used, its outcome and its cost, so the baseline is found by measurement and does not rest on assumed values. The plan's assumptions reach the user interface:
   - Each plan's assumptions, such as the default, the chosen path, rejected alternatives and an estimate against the actual, are engine-reported data.
   - Connectome renders them through triggered A2UI components.
   - An advanced-view toggle makes every AI action transparent, with visual components generated from that machine data.

   That UI work belongs to the Connectome packages that consume J1 and J5's reports.
4. **Reasoning grows in cycles, scaled by effort (J11, J12).** In the owner's words: "QL is suppose to do cycles and grow and grow in one session depending on the effort slider. We get the 8-12 second marker be the target for our baseline default that would produce strong planning and accuracy and show actually not the fastest solution but the users preferences."
   - **The slider is the existing effort contract.** It is not a new one. Presets expand into sealed numeric limits under the [user-selected effort contract](../reference/inference/lfg-swag.md#user-selected-effort-and-run-budgets), and every cycle consumes the one durable task budget. Retries, restarts and UI reloads never create a new allowance.
   - **8 to 12 seconds is the Balanced target, calibrated by measurement.** It is not a hardcoded constant. On a fixed question set, measure evidence and answer quality against wall time for each difficulty band. Set Balanced where quality flattens with p50 near 8 s and p90 at or under 12 s, and record that decision under decision 3.
   - **Preferences shape the answer, visibly.** Stored preferences and memories, such as the owner's hypermodular colocated structure, canonical consistency and no hardcoding beyond best practice, are fetched in their own recorded cycle step through the existing preference resolution. The replay shows which preference changed which choice.
   - **The graph is replayable.** At recorded stamps, engine retrieval replays exactly. Model output is retained, so a replay either re-renders the stored graph or re-executes it under a new configuration.
   - **Traces are ephemeral.** They are dropped under resource pressure, and dev mode keeps the last N for review (J12).
   - **The customer view is plain; the depth is one drill-down away.** It shows the answer, its sources, a confidence label and short per-cycle summaries ("looked in X, found Y, checked Z"). The developer view shows the trace tree, a timeline, per-document scores and replay (H-06). Private model reasoning is never shown, only its summaries (ADR-0002).

## 6. Research

- SurrealDB vector forms `<|K,EF|>` and `<|K,METRIC|>`, filters pushed into KNN as shown by `EXPLAIN`, and the 4.0.1 change from silent fallback to error ([operators](https://surrealdb.com/docs/surrealql/operators), [similarity search](https://surrealdb.com/docs/learn/data-models/vector-search/similarity-search)).
- ArangoDB 3.12 vector index (IVF) with `APPROX_NEAR_*`, the FILTER restrictions, and cost-based plan selection ([vector indexes](https://docs.arango.ai/arangodb/3.12/indexes-and-search/indexing/working-with-indexes/vector-indexes/), [optimizer](https://docs.arango.ai/arangodb/3.12/aql/execution-and-performance/query-optimization/)).
- Qdrant prefetch with RRF, DBSF or formula fusion; filterable HNSW; a per-segment planner choosing full scan, payload index, graph or ACORN by cardinality ([hybrid queries](https://qdrant.tech/documentation/concepts/hybrid-queries/), [indexing](https://qdrant.tech/documentation/concepts/indexing/), [filterable HNSW](https://qdrant.tech/articles/filterable-hnsw/)).
- ACORN ([arXiv 2403.04871](https://arxiv.org/abs/2403.04871)), Filtered-DiskANN ([WWW 2023](https://dblp.uni-trier.de/rec/conf/www/GollapudiKSKBRL23.html)), and RRF ([SIGIR 2009](https://research.google/pubs/pub36196/)).
- Hot-then-cold reads at one stamp: Neon's GetPage@LSN ([pageserver](https://github.com/neondatabase/neon/blob/main/docs/pageserver-storage.md)), RocksDB's time-aware tiering ([blog](https://rocksdb.org/blog/2022/11/09/time-aware-tiered-storage.html)), and TiFlash's read-timestamp wait ([overview](https://docs.pingcap.com/tidb/stable/tiflash-overview/)).

- Iterative retrieval and when to stop: ReAct's step cap ([arXiv 2210.03629](https://arxiv.org/abs/2210.03629)); IRCoT's query from the last reasoning step, with step and evidence caps ([arXiv 2212.10509](https://arxiv.org/abs/2212.10509)); FLARE's confidence-triggered retrieval ([arXiv 2305.06983](https://arxiv.org/abs/2305.06983)); Self-RAG's tunable retrieve and support thresholds ([arXiv 2310.11511](https://arxiv.org/abs/2310.11511)); Adaptive-RAG's routing by query complexity ([arXiv 2403.14403](https://arxiv.org/abs/2403.14403)); and compute-optimal allocation by difficulty ([arXiv 2408.03314](https://arxiv.org/abs/2408.03314)).
- Deadlines: contract and interruptible anytime algorithms, with performance profiles ([Zilberstein 1996](https://doi.org/10.1609/aimag.v17i3.1232)), and online stopping by predicted gain ([IJCAI 2018](https://ijcai.org/proceedings/2018/208)). Vendor effort controls are soft targets beneath a hard ceiling ([OpenAI reasoning](https://developers.openai.com/api/docs/guides/reasoning), [Anthropic effort](https://platform.claude.com/docs/en/build-with-claude/effort)).
- Traces: OpenInference span kinds and attributes ([semantic conventions](https://github.com/Arize-ai/openinference/blob/main/spec/semantic_conventions.md)); Phoenix sessions, span replay of model calls only, and count- or day-based retention ([sessions](https://arize.com/docs/phoenix/tracing/llm-traces/sessions), [span replay](https://arize.com/docs/phoenix/prompt-engineering/overview-prompts/span-replay), [retention](https://arize.com/docs/phoenix/settings/data-retention)); OpenTelemetry tail sampling with bounded memory and counted early drops ([processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/tailsamplingprocessor/README.md)); and Go's flight recorder, an in-memory ring snapshotted on a trigger ([blog](https://go.dev/blog/flight-recorder)).

Each package adapts behavior to RRFlow's own types, stamps, budgets and tests, as AGENTS.md requires. It copies no upstream code.
