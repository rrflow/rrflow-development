**Coordinate:** `rrflow://rrflow-instance/data/architecture/rroflow-sdk-and-bridge-plan`
**Owner:** H-04 SDK projections, D-06 integration and I-01/I-04 observation; roadmap owns order and status

This extends the [one-engine plan](one-engine-execution-plan.md) for an easy, explicit bridge from AI tools and application SDKs into RROFLOW. The [README](../../README.md), [alpha objective](../objectives/rrflow-1.0-alpha.md), [roadmap](../roadmap/rrflow-1.0.md), [dependency spine](../roadmap/rrflow-1.0/executable-dependency-spine.md), and [POA&M](../poam/rrflow-1.0-alpha.md) remain the owners. This is a design and execution handoff, not an implemented API, activated collector, new status ledger or replacement for those owners.

## Desired experience and actual boundary

An installed RRFlow estate works offline without a provider. From a project the operator can preview an integration, see the exact source, supported event and content classes, destination, identity, permissions, configuration changes, budgets and uninstall behavior, and explicitly activate the desired binding. A planned launch command or an explicitly configured provider exporter connects supported sessions to the local engine; a typed application SDK offers the same engine operations to applications. Names and syntax in this section are design targets, not existing commands.

Project/boundary capture is the default. An optional, explicitly configured per-user global bridge can route eligible enabled sources across multiple authorized estates, but its scope is the registered sources and configured sessions, not arbitrary applications, accounts, past conversations or machine-wide interception. Each accepted event is bound to one estate and its engine authorization. A global view joins only estates the reader can access and is not a new engine, write authority or blanket cross-project grant. Unknown or conflicting identity is held or dropped under a bounded policy with a visible count; it is never silently assigned to a default estate. If a provider cannot attest a project's identity for each event, bind the authorized session to its launch estate and require explicit rebind when the operator changes scope; do not guess from untrusted metadata.

The owner has asked for both project-default and global options; that selects the design direction, not authorization to alter provider configuration, read secrets or activate capture. Until the content decision is made, assume metadata-only with separately previewed and authorized content. Even metadata may contain sensitive data; apply classification, limits and redaction before persistence. Collection, content, remote export, training and promotion have separate grants. User-facing status distinguishes disabled, configured but inactive, starting, active, partial, degraded, revoked and unsupported, with observed coverage, delays, drops and unknowns rather than a connected badge implying completeness.

## Existing code and provider facts

- `crates/authority/rrd-engine/src/engine/observation_source.rs` owns authenticated preview/apply/read of configuration for an installed estate. Its own module states configuration is not collector activation. [Gate I](../roadmap/rrflow-1.0/gate-i.md#provider-observation-for-rroflow) identifies the still-open canonical event, adapters and readback. No verified end-to-end provider collector is established by this plan.
- `rrd-contract` owns the endpoint catalogue; `rrd-server` dispatches it. `sdks/typescript`, `python`, `go`, `java`, and `dotnet` and the Rust `rrd-client` exist. [Generated surfaces](../roadmap/rrflow-1.0-execution/generated-surfaces.md) records that endpoint generation remains split, the Rust client is handwritten, and full generated models and H-04 conformance remain open. `scripts/ci/run_sdk_conformance.py` exercises a declared corpus against a real daemon on its supported environment; it is not evidence for all operations, providers or platforms.
- On this Windows host, Python reports `0666` even after a temporary file is chmodded `0600`; the shared SDK harness unconditionally demands `0600`, while its Rust writer does not establish a protected non-Unix DACL. This verified portability and permission gap is recorded in [POAM-011](../poam/rrflow-1.0-alpha/poam-011.md). A native repair must preserve real access isolation rather than skip permission validation.
- [Codex telemetry configuration](https://learn.chatgpt.com/docs/config-file/config-advanced#observability-and-telemetry) documents opt-in OTLP log export; user prompt logging is separately controlled. [Claude Code monitoring](https://code.claude.com/docs/en/monitoring-usage) documents opt-in telemetry with separate content controls, and some detailed trace fields are beta. [Grok headless scripting](https://docs.x.ai/build/cli/headless-scripting) documents streaming JSON and ACP for controlled sessions. Their settings and coverage differ: qualify the actual tool version, event families, transport and content available. Do not imply a universal Grok OTLP feed or capture of hidden reasoning. More frontier tools can join through a documented adapter contract; unsupported surfaces remain explicitly unsupported.
- [OTLP](https://opentelemetry.io/docs/specs/otlp/) specifies retry and partial-success behavior, not lossless delivery across the complete provider-to-engine chain. Record actual exporter limitations and uncertainty. [Rust targets](https://doc.rust-lang.org/rustc/platform-support.html) and [GitHub-hosted runner labels](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) establish toolchain/runner availability, not RRFlow support or evidence that a native run took place.

## One admission path and scope identity

An integration is discovered inactive. The engine previews and authorizes a versioned binding with estate, principal, source identity/revision, supported transport and event classes, selected content classes, credential reference, endpoint, redaction, retention, rate and storage limits. Activation is an explicit auditable effect. Local receivers authenticate the producer and binding; source-declared names, paths or OTLP resource attributes alone are not grants. Do not expose credentials in SDK errors, logs, configuration previews, evidence or generated files. Do not automatically modify provider settings or install provider/editor hooks.

The bridge validates bounded input, redacts before persistence, translates supported source records without inventing their semantics, and submits them through the canonical I-01 engine admission. The engine owns accepted events, duplicate decisions, durable receipts, source revisions, retention and audit. A source record carries version, estate, binding/revision, authenticated producer, provider/version, event class/time, available source/session identity, provenance, authorized content references or digest, and explicit missing/uncertain fields. Unknown event kinds are visibly unsupported unless an admitted versioned extension permits them. Provider metadata and derived tags do not themselves authorize effects or prove success.

Stable source event identity is used when the source actually supplies it. A durable stream checkpoint may establish identity only when that transport proves the checkpoint stable across reconnects. Where neither exists, label deduplication and coverage best-effort; never fabricate exactly-once delivery. The engine commits accepted events, deduplication identities and applicable checkpoints/receipts atomically when supported. Same identity and payload replays to its prior result; changed payload conflicts. A lost response is reconciled against engine readback. Queue exhaustion, partial OTLP success, out-of-order events, rejected records and source loss are visible and bounded. A collector cannot claim complete coverage simply because it is running.

Global mode is a routing configuration for explicitly enabled sources, scoped by a user and per-estate grants. Bind each incoming source/session to its allowed estate with an authenticated route; engine acceptance still checks current binding revision, permissions and retention at each effect. Revocation fences new acceptance and does not silently erase retained receipts. No global route can broaden a project grant. Changing workspace, editing source configuration, or revoking access triggers re-evaluation of affected effects and a versioned successor where necessary; unrelated estates continue only when their dependencies and grants are independent. Unknown identity is bounded and observable, and operator-driven reassignment requires authorization and audit.

## SDK contract

H-04 converges the existing catalogue, wire types and validators into a single versioned generation entry point for Rust internal bindings and TypeScript, Python, Go, Java and .NET operations/models, OpenAPI and reference/conformance projections. Language SDKs retain only idiomatic transport, cancellation, resource lifetime and packaging. A binding cannot manufacture an operation, bypass engine authorization, own a durable plan or claim capture merely because a generated method exists. Publish versioned capability discovery and typed errors, including unavailable, denied, stale, partial, uncertain and retryable results. Retry only with operation-specific idempotency semantics; cancellation must report whether an effect was actually stopped.

Ship a small, documented project example per language: connect to an already running engine, identify the project, preview a source binding, and inspect the plan/status/receipts using only operations actually available at that release. When observation admission exists, add the same normalized-event and denied-scope example in every SDK. Fixtures and generated model compilation cannot substitute for real installed-engine conformance. The SDKs do not bundle provider credentials, require a cloud service, or spawn an independent lifecycle store. Support matrix entries must include SDK version, runtime/toolchain, OS/architecture, server version, passing corpus and unsupported features.

## Native sequence and evidence

Implement and qualify Linux and Windows x86-64 and ARM64 first; macOS x86-64 and Apple Silicon follow. ARM is a processor architecture, so Linux ARM64 and Windows ARM64 are independent cells. Candidate target triples include `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc`, `x86_64-apple-darwin`, and `aarch64-apple-darwin`; confirm dependency availability and actual native execution before advertising any cell. Cross compilation and emulation are useful preliminary checks, not native qualification. Hosted ARM64 labels may help ordinary CI, but runner configuration, architecture, resource limits and availability must be observed in the actual run. A hosted runner is not automatically representative capacity hardware.

For each claimed native cell retain exact source/tree, binary and harness digests, OS/version/CPU architecture, native process architecture, toolchain, runtime, configuration, provider version, workload, results and artifact location. Run install/offline start, project identity and isolation, SDK corpus, bridge activation/revocation, restart/replay, uninstall and native filesystem/process/resource limits. Fault, capacity, 100 reopens and 24-hour soak remain the distinct [C-07 requirements](../roadmap/rrflow-1.0/gate-c-07.md): bridge CI does not close them. Unsupported or unrun matrix cells remain unqualified. Prior Windows 100,000-record characterization failed its sampling gap; it is not an accepted C-07 operating point.

## Decisions and integration proof

The content default remains an owner decision; metadata-only with individually authorized content is the planning assumption. The first real provider pilot and credentials/machine are also undetermined; work that does not require a provider remains independent. Exact per-user global configuration API, consent interface, provenance for ambiguous source attribution, retention periods, and quantitative latency/recall/resource budgets require design and measured baselines in their owning packages. No answer to these questions is assumed to authorize a live integration.

The first joined acceptance must install a real engine into two project estates; activate only one qualified source per selected binding; observe a real supported event; read its event, scope, source revision, memory/signal and audit through at least two SDKs; restart the engine and bridge and replay; verify no cross-estate leakage or duplicate accepted event where stable identity is supported; revoke and prove subsequent admission is denied. A real content-enabled run must show that unauthorized content is absent. If any provider, event class, stable identity, native platform or toolchain is unavailable, preserve the reason and mark that cell unrun. This checkpoint does not close H-04, I-01, I-04, C-07 or alpha without their owning acceptance evidence.
