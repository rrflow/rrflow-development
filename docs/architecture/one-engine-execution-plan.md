# One-engine execution and verifiable handoff plan

**Status:** active proposed supporting plan; runtime and CI enforcement not established
**Coordinate:** `rrflow://rrflow-instance/data/architecture/one-engine-execution-plan`
**Owner:** supporting execution design for OBJ-14 and the existing roadmap

This proposal supports the [README](../../README.md), [alpha objective](../objectives/rrflow-1.0-alpha.md), [release roadmap](../roadmap/rrflow-1.0.md), [dependency spine](../roadmap/rrflow-1.0/executable-dependency-spine.md), and [POA&M](../poam/rrflow-1.0-alpha.md). Those records own identity, outcome, order and status. This is not a second roadmap, lifecycle, plan authority or status ledger. The proposed [handoff schema](schemas/one-engine-handoff-v1.schema.json) and [illustrative example](examples/one-engine-handoff-v1.json) are design artifacts only. No check, product operation or safeguard is active merely because this file or schema exists.

## 1. Required experience

One installed RRFlow estate admits an authenticated task; gathers relevant authorized context; records a versioned, effect-scoped plan when work becomes durable or externally observable; asks only questions needed by an effect; and supports useful authorized background work while other questions remain open. `RrdEngine` owns plan acceptance, source/configuration identity, budgets, decisions, progress, mutation, durable receipts, and memory/audit readback. `rrflowDB` is the semantic estate, `rrflowKV` its durable profile, and `rrflowQL`, graph/lexical/vector paths and optional Arrow/DataFusion execute against engine-selected stamps. Connectome and provider clients consume engine operations. LFG/SWAG can propose analysis and select among admitted capabilities, never grant permission or become the owner.

Exploration, provisional reasoning and harmless reads stay adaptive under [ADR-0002](../decisions/0002-adaptive-reasoning-governed-effects.md). A plan describes observable effects and evidence, not chain-of-thought. A public or external effect must have explicit scope, identity, policy and authorization; unavailable facts block only dependent effects.

## 3. Handoff design and enforcement

There are two related boundaries. The **repository package handoff** projects the existing PR brief, Git identities, journal and CI results into a checkable receipt. The **product work handoff** is accepted and persisted by `RrdEngine` as an engine-owned plan/effect record. A repository receipt is never a product job, and a model, provider, editor, Git hook, schema file or UI is never a lifecycle authority. The schema is a proposed common envelope shape; production types and generated projections must have one executable owner, not independently maintained duplicate schemas.

At a handoff, the receiver obtains the exact plan version and immutable content digest, sender/receiver and project/estate identity, source scope and completeness, effective configuration, policy/approval, budgets, effect list, question dependencies, verification and prior receipts. Each effect has a stable identity, capability, input dependencies, allowed target and observable expected result. This does not encode the model's thinking.

Plans are tailored to the actual request and available capabilities rather than generated from a fixed project template. For example, a request to understand a local project may permit bounded source discovery while an optional external-connector question remains open; only the connector-dependent effect waits. A request to modify a file additionally needs a source-bound mutation effect and the applicable native publication guarantee. The handoff binds task and request identity without automatically retaining the prompt; hashes and references can themselves be sensitive and require access control. Per-effect limits must also fit an engine-enforced aggregate time, memory, retry and spend budget shared across retries. Unknown usage is not zero.

The future contract must specify a versioned, domain-separated digest algorithm over the exact immutable plan payload, excluding its own digest and detached approval/receipt. Preserve existing `attunement_plan_sha256` identities; do not silently substitute a different encoding. Evaluate [RFC 8785 canonical JSON](https://www.rfc-editor.org/rfc/rfc8785) against RRFlow's existing domain-separated encoding and cross-language numeric limits, then select and document one format for each new type with independent golden vectors. Reject duplicate keys, unsupported numbers and mismatched encoding versions. The handoff's `plan.sha256` is a reference to that separately stored plan, not a claim that hashing this envelope proves approval.

For **each actual change**, later implementation must:

1. Verify the applicable planned effect, current plan digest, source/configuration/policy identity, authorization and unresolved question dependencies. An incomplete dependency inventory cannot justify a claim that an edit is unrelated.
2. Bind the concrete action and idempotency identity to that effect. Refuse an unknown effect or changed scope; a material change needs a new plan or approved amendment. A retry after an uncertain external outcome remains uncertain until the capability can reconcile it.
3. Carry plan/effect identity through engine admission, execution and receipt. Compare independently observed effects and post-effect readback with the approved effect. An agent assertion or generated action list alone is not proof. Audit and memory write/read receipts bind principal, plan, relevant sources, effect and outcome without leaking secrets.
4. For repository changes, use the existing PR and journal as owners. A future required candidate-CI check validates a versioned projection against the PR base/head, plan digest, actual Git diff, owner paths, required test results and independently retained artifacts. Reject missing, stale, mismatched, unauthorized or unaccounted files/effects. Generated files must link to their generator and owner. Protect the validator and required checks, validate from an independently trusted base, and review policy changes as their own package. This does not prevent an agent editing local files, prove private reasoning, or defend against an authorized party changing the protected policy. Do not use provider/editor-owned hooks.
5. Bind repository result receipts to the candidate head **outside that head's committed bytes**, such as a CI artifact/check tied to the exact PR head. Do not put a commit's own hash inside that commit or hash a record including its own hash. The verifier independently recomputes hashes, checks authorization, observes effects and evaluates proof.

The schema's lifecycle labels are handoff observations, not an additional state machine; engine or GitHub state remains authoritative. The example is fictional and cannot authorize a real project. Schema validity alone establishes neither approval, source freshness, test execution, safety nor completion.

The semantic verifier, not JSON Schema, must also require unique effect/question/input IDs, resolve every dependency, compare approval and receipt plan digests with the accepted plan, authenticate sender/receiver/grant, validate expiry and budget, ensure every successful effect has appropriate independent evidence, reject failed/uncertain evidence as success, and compare the actual diff/effect set with scope. It must check calendar-valid UTC timestamps even when a JSON Schema implementation treats `format` as annotation. The supplied example deliberately contains placeholders and is not a test run. Never execute arbitrary command strings supplied by a handoff: CI and capability runners use separately admitted commands and sandbox/budget policy.

## 4. Ordinary edits, questions and uncertainty

Git HEAD is useful provenance but misses uncommitted work. Bind admitted working-tree content and complete scoped dependencies for a durable claim; non-Git projects have no invented commit. Keep source revision, snapshot digest, parser/model/configuration versions and grants distinct.

On a relevant edit, refuse the dependent mutation before prohibited domain/project effects, identify affected sources, capture a new allowed boundary and produce a new immutable plan with predecessor, change summary and digest. CAS acceptance fences old workers. Preserve old plans and receipts. Carry approval forward only when principal, scope, policy, expiry and effect still authorize the unchanged action. Unrelated effects may continue only with proven unaffected dependency closure. Replan must not require reinstalling or deleting the estate. Cancellation, inspection and recovery remain available while stale or paused.

An open question is a versioned engine record; each effect names exactly its blocking questions. Unrelated authorized work may continue. Answering is authorized and audited; an answer that changes the plan produces a successor. The UI reports known, running, waiting, stale, failed, canceled and uncertain work, possible next actions and retained memory effects. Never claim hidden reasoning was captured.

Hash-then-write does not eliminate a concurrent editor race. A project mutation adapter must demonstrate conditional publication or writer exclusion for its exact native filesystem and effect, including path substitution. Otherwise present the proposal and refuse the stronger safety claim. A stored snapshot supports a snapshot-relative answer without claiming live source still matches. Resolve how an authorized audit write relates to the stale-effect no-domain-write oracle without hiding either.

## 5. Executable packages and acceptance

The [SDK and launch-bridge plan](rroflow-sdk-and-bridge-plan.md) expands P7 and H-04 into independently reviewable packages, project and global routing, real provider coverage, and native platform qualification. It is a supporting design, not a new dependency or status owner.

The dependency spine owns ordering. Rows below map it into separately reviewed PRs; split them further at natural boundaries. Each PR brief names exact files/symbols and real commands before editing, begins with a missing-behavior or failure oracle, records a linked journal and has candidate CI. A planned test target must be created before its command can run; never report a proposed test as executed.

P0 is the first proposed repository guard package. It can start from the existing `scripts/ci/check_workflow.py` and `scripts/ci/test_candidate_admission.py`; a proposed new `scripts/ci/validate_change_handoff.py` and `scripts/ci/test_change_handoff.py` are implementation targets, not files claimed to exist. The package must decide and document how a trusted base validator receives PR metadata and a detached exact-head receipt in both pull-request and merge-group contexts, without executing a candidate-supplied command. Bootstrap that one validator change through the existing PR/journal/full-CI gate, then require it for later packages. If trusted execution or required-check configuration cannot be established, report the gap and do not claim enforcement.

P0's independently controlled verifier should enumerate changed paths and blob identities from Git, compare them with typed per-effect resource selectors and owner scopes, and bind the actual CI-produced test/artifact identities to the candidate head. Path normalization, symlinks, renames, binary files, generated paths, missing dependencies, broad prefix selectors, merge-group heads and changed base/head require explicit behavior. A check must not trust a PR-authored `passed` flag or execute commands from the handoff. A protected validator/policy change needs separate review and must not validate itself solely with candidate-supplied rules. A pass means the declared checks succeeded under the documented trust boundary, not that an LLM understood the plan or that no bug exists.

### C-07 qualification matrix

The [C-07 owner](../roadmap/rrflow-1.0/gate-c-07.md) and [J-04 workload ladder](../roadmap/rrflow-1.0/gate-j.md#initial-workload-ladder) own thresholds and applicability. They currently specify Desktop (4 vCPU, 2 GiB engine RSS ceiling, 100,000 records and vectors), single service (8 vCPU, 8 GiB ceiling, one million records and vectors), ten-estate fleet isolation, and data larger than memory. These are laboratory targets, not measured product capacity. Before a measured run freeze actual environment, source/tree/binary/harness/configuration/corpus digests, limits and seeds. The C-07 storage projection uses 50% point reads, 20% bounded range reads, 25% atomic mixed-family writes and 5% checkpoint/backup/cancel; storing vectors or relations does not prove ANN quality or graph traversal. The fuller J-04 semantic mix is separate.

Required coverage includes native correctness and bounded memory on Windows, Linux and macOS; cold/warm, backup-under-write and reader-pin/maintenance lanes; at least 100 forced reopens per admitted operating point; 5-minute warmup, 30-minute measured intervals and at least three seeded repetitions; 2x load and drain; constrained memory; and an actual 24-hour sustained soak. Record each native storage-full/error and recovery case, acknowledgement class, resource series and unsupported cell. Larger runs qualify only the platform and allocation actually tested. Do not substitute a prior head, a short smoke, a timer or a synthetic fixture for final-candidate evidence.

### First independently checked joined journey

Create a small fixture with independently enumerated source bytes, expected spans/relations and a known-answer query. Install in existing-project mode, preview and authorize a plan, start a real background job, ingest source, query via rrflowQL and vector/graph paths at one stamp, read a memory and its receipt, edit and delete inputs, replan, interrupt and restart, replay, and compare independently observed files, stored records, receipts and audit. Repeat for a second estate with conflicting names. This is the first product checkpoint, not C-07 scale or full alpha proof. The proposed larger real-project candidate is RRFlow itself unless the owner chooses another.

### Existing checks and planned tests

Existing baseline commands include `cargo test -p rrd-engine --test engine_authority one_authority_coordinates_security_data_catalogues_audit_and_reopen --locked`, `cargo test -p rrd-client --test rrflowdb_local installed_attunement_cancel --locked`, `cargo test -p rrd-contract --test attunement_contract --locked`, `python scripts/knowledge/render_navigation.py --check`, and `python scripts/ci/build_execution_inventory.py --check`. They do not implement the missing plan or indexing. Create targeted integration and installed-process tests in each implementation package; run the smallest first, then owning suites and candidate CI. Evidence is tied to exact heads and artifacts, never transferred automatically to another candidate.

For a public-operation change, run the contract, server and client suites, regenerate and check all SDK projections and shared conformance, and run `cargo test -p rrflow-eval --locked`: its synthetic storage fixtures bind the public catalogue digest. If that digest changes, use the existing `cargo run -p rrflow-eval --example refresh_storage_contract --locked` synthetic-only generator, review exactly what it changed, and retain real native evidence untouched. PR172's initial failure demonstrates why these cross-boundary checks belong in the package, not only CI.

## 6. Sonnet-ready handoff instructions

The receiving agent reads `AGENTS.md`, README and linked owners, checks worktree/diff and remote main, then opens the named PR brief. Compare the handoff plan digest and live identities; do not assume this review baseline is current. Select the first package with satisfied dependencies; identify existing files and missing behavior. If a necessary public operation, policy or source completeness is unknown, record a scoped question and continue unrelated authorized exploration. Do not synthesize approval. Implement only that package, characterize failure before repair, use one PR and journal, run the focused oracle then affected suites, review the full diff, preserve failures and push only to the public development remote. Await candidate CI and protected merge queue. Handoff exact PR/head, actual evidence, unresolved unknowns and next package. If a test contradicts the plan, stop the affected effect and propose a successor.

## 7. Decisions still needed

1. Which real project follows the independent fixture? Default proposal: RRFlow itself. This affects the later real-project run, not the fixture or plan.
2. For the first RROFLOW pilot, which providers and content classes are authorized: metadata first, or selected conversation/tool content? Record provider-specific availability, retention and redaction. Default proposal: metadata first and separately authorize content; historical coverage is not assumed.
3. What finite budgets, credentials, destinations and access grants apply to a particular estate? These are per-estate inputs. A missing value blocks only the associated effect.
4. Global configuration operations remain unresolved. Select their owner/admission and grant in D-02c before a public settings mutation; job-control authorization does not answer this.
5. Define the native conditional project mutation primitive and resolve the D-03 unchanged-rerun versus adversarial same-metadata-edit requirement through platform evidence. These are engineering experiments, not questions the user must solve up front.

## 8. Research and limits

- [Bazel Skyframe](https://bazel.build/reference/skyframe) tracks dependencies for invalidation and change pruning. RRFlow can adapt that principle only when its own dependency coverage is complete.
- [AWS idempotent API design](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) explains stable request identity and atomic effect/receipt recording. Remote providers may not offer that property; unknown outcomes need reconciliation.
- [JSON Schema conditionals](https://json-schema.org/understanding-json-schema/reference/conditionals) validate structure, not truth or execution. [in-toto attestations](https://github.com/in-toto/attestation/blob/main/spec/README.md) bind claims to subjects; signed claims still require trusted issuers and independent verification. No new signing system is assumed.
- [Qdrant quantization](https://qdrant.tech/documentation/manage-data/quantization/) documents dataset-dependent tradeoffs and rescoring; rescoring cannot recover omitted candidates. [Google TurboQuant research](https://research.google/blog/turboquant-redefining-ai-efficiency-with-extreme-compression/) motivates measurement, not an RRFlow performance claim.
- [Claude Code monitoring](https://code.claude.com/docs/en/monitoring-usage) and [Grok headless streaming](https://docs.x.ai/build/cli/headless-scripting) describe distinct opt-in surfaces; actual version and content coverage must be tested.

This is a proposal. Its safeguards, installed journey, capacity and alpha claims remain unimplemented or unqualified until their named packages and evidence pass.
