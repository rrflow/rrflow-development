# D-04 Windows parser pipe foundation

**Status:** active draft component; installed Parse remains unavailable
**Coordinate:** `rrflow://rrflow-instance/data/evidence/change-journal/gate-d/d-04-windows-parser-pipes`
**Owner:** D-04 / [PR #241](https://github.com/rrflow/rrflow-development/pull/241), prerequisite to the installed project-to-query objective

Starting candidate `b5fa4499da1a7932197e2130d73501701a16ab16`, tree `f46c1cab27d4ede0382bbce8969ffc1c4afc907a`. The PR brief was extended before implementation. The installed Parse driver fails with `phase-unavailable`; the existing Windows job supervisor had no standard input or output, so it could not transport the existing framed parser protocol. This change adds a private, piped launch to the existing supervisor using non-inheritable parent pipe ends, inheritable duplicates for exactly the child ends, a distinct null stderr sink, and a Windows process attribute list combining those handles with the pre-associated memory-limited job. The old no-I/O launch remains. This is not wired into engine dispatch and does not alter authorization, source reading, public contracts or publication.

The complete changed files were reread and the diff reviewed: `crates/authority/rrd-engine/Cargo.toml` (prior blob `e38570d18c029e59266b3824632e1ba24db0b8bf`), `src/engine/attunement/windows_supervisor.rs` (`5c16f7618b25fb1b312eb2efd63b5c1dcf71fa92`) and its `tests.rs` (`8975e684efec728950c87911b6b884e0295e9bbd`). The framed worker, existing installed driver, native containment, package owner and candidate status were also inspected; these are not a whole-repository review. No production implementation was deleted or moved. The Cargo feature enables Windows' existing pipe API; no dependency tree or generated protocol changed.

The implementation follows Microsoft's documented [explicit child handle list](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) and [anonymous pipe semantics](https://learn.microsoft.com/en-us/windows/win32/ipc/anonymous-pipe-operations). A synchronous pipe write can block until read or the peer closes; the tests explicitly terminate a non-reading job and require the blocked writer to return. No upstream code was copied. No runtime trace or persisted effect was added: child job association, the parser response and process exit are the component evidence.

The handle list restricts **this** child. Windows requires the selected duplicates to be inheritable, and a different process launched concurrently with blanket handle inheritance could receive them; this has not been prevented or qualified in an embedded host. The executable is still selected by path and is not bound to an admitted file identity at launch; the child also inherits the parent environment. The pipes have no integrated deadline, bounded reader/writer owner, source freshness/authorization/lease recheck, or durable publication. Named pipes are an unproven alternative, not a completed solution: Microsoft's [security documentation](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights) notes that the default descriptor grants broad read access, so a private authenticated endpoint would need its own admission and spoofing tests. Keep Parse unavailable until these boundaries and platform equivalents are resolved.
