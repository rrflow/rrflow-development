## Observations and research

At `2026-10-29T02:53:03Z`, a GitHub API snapshot of 16 active runs contained 14 PR candidates and two merge groups; 188 jobs were queued, including 26 macOS jobs, with five macOS jobs running. The full local snapshot is `target/ci-queue-snapshot-20261029.json`; it is a time-specific observation, not a persistent runner-limit measurement. `gh cache list --ref refs/heads/main` returned zero entries at this point, while the cache usage API reported 13 entries and 12,363,095,916 bytes. Later PR caches continued to appear. An earlier macOS candidate/merge observation found a roughly 42.5-minute release build and 1.1-minute 100-cycle step. Different job starts and cache eviction can affect comparison; these numbers do not prove this experiment will improve latency. In PR167 candidate run 40800937024, its last substantive job finished at 02:23:36 UTC while the aggregate gate remained queued past 03:05 UTC. This observes the full dependency wait and runner queue, not aggregate test execution time.

[GitHub's cache scope documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching) states PR-created caches are scoped to the merge ref and documents default-branch fallback. [GitHub's runner documentation](https://docs.github.com/en/actions/using-github-hosted-runners/using-github-hosted-runners/monitoring-your-current-jobs) describes queued jobs when concurrency limits are reached. [The pinned rust-cache documentation](https://github.com/Swatinem/rust-cache/tree/v2.9.2) describes shared keys and toolchain-based keys. No upstream implementation was copied; the existing workflow is the exact behavioral source.
