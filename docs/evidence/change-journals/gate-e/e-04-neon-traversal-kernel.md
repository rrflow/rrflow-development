change brief (current -> target behavior, owner, exact scope, unchanged behavior, stop conditions): the description of pull request #285. HnswKernel::Auto had an AVX2 kernel for x86_64 and scalar f64 arithmetic everywhere else, so every aarch64 host scored traversal one float at a time. Traversal on aarch64 now uses NEON, and both SIMD kernels compute only what their metric needs. A SIMD score that is not finite, or a cosine norm outside the normal f32 range, gets the scalar kernel's score. Construction stays scalar, so artifact bytes stay portable, and final scores still come from the exact reranker.
files and symbols read in full: rrd-vector hnsw.rs (score_dense_values, score_dense_avx2, search_candidates_with_kernel, greedy_layer, search_layer), exact.rs score_dense, runtime.rs's HNSW rerank, tests/recall_gate.rs, the native-arm64 job in ci-reusable.yml, docs/reference/vector/hnsw-projection.md and search.md.

research decision and primary-source/adaptation record: none new. These are Arm NEON intrinsics from std::arch, and no code is adapted from another project.

surfaced failures and corrections: the kernel is about sixteen times faster alone and the headline number barely moves. Plain search at ef-32 with one client is within run-to-run variation, which the alternating runs show to be large, 157.1 to 194.4 on identical settings. Eight clients do not move, which fits audit commits being the limit there. The profile said score_dense was 19% of CPU time, but that own time includes waiting on cold vector memory, which SIMD cannot remove, and traversal at ef-32 scores few vectors. The clear gains are where a search scores more: filtered search with one client gained 27% to 37% on COCO, with p50 from 22.98 to 17.21 ms at ef-128. I had expected more from plain search, and said so before measuring it. The AVX2 changes were not measured in the lab, because no lab host is x86.
checks not run and reason: candidate CI, because it skips drafts; its native-arm64 and macOS jobs will run NEON and its Linux and Windows jobs AVX2. A repeat of the COCO A/B. AVX2 timing or any real run on x86. An exact_rerank other than 10.
remaining known errors and owner: the other x86-only kernels remain scalar on ARM, in compact.rs, quantized_segment.rs and turboquant.rs, and each needs its own measurement. Traversal still loads each graph vector from separately allocated memory, the likely next cost in this path. f32 lanes round differently from scalar and between architectures, so a candidate near a tie can differ; the exact reranker decides every final score, and recall_gate.rs asserts that automatic and scalar results match. A run's mean is well below what its median implies at some settings, for example ef-64 on COCO: p50 7.87 ms implies about 127 and the run achieved 92.5. Those cases hold several separate stalls of 400 to 960 ms, in searches that otherwise take under 12 ms, and p99 does not show them. They are storage flushes and compaction holding the exclusive lock, and searches cause them: the engine wrote about 21 KB per search by /proc write_bytes, on a run that only searches, which counts whole pages and so overstates logical bytes. On vector-small, raising wal_flush_target_bytes to 4 GiB moved them: plain ef-64 with one client went from 115.8 to 164.1 with a maximum of 9.9 ms in place of 623.6 ms, and the stall arrived later instead, at ef-128, with a matching burst of writes. One run of each. Audit commits remain the owner's decision. Building segments outside the exclusive lock is a storage package of its own, with recovery risk, and is not started.
