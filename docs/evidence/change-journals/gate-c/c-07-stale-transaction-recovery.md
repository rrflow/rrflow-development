That run found two rejected leases at expected cursor 28872 with actual cursor 28879; their effects were independently absent. The [PR brief](https://github.com/rrflow/rrflow-development/pull/214) preceded this change. The prior engine returned a generic storage conflict with `retryable=true` even when this exact commit was proven absent and the runtime cursor had advanced. The first real installed test with the required non-retryable response failed on that flag, confirming the gap. This observation does not identify the internal store branch or establish the cause of the separate latency breaches.

`rrd-engine` now classifies `RuntimeConflict` as `TransactionSnapshotStale` only inside the transaction commit path after exact-outcome lookup returned absent and only when `actual > expected`. The established rejection path clears the intent before returning, and the client must still explicitly abort. Equal or lower cursors and unrelated conflict variants retain their earlier generic handling; unknown/uncertain outcomes are not converted to definite rejection. `rrd-server` projects the same HTTP and WebSocket `conflict`, `retryable=false`, fixed reason `transaction-snapshot-stale`, action `abort-and-reexecute-transaction`, and numeric cursor details already present in public leases/receipts. The protocol reference documents redoing the complete read/decision/write transaction; no automatic rebase or retry is added. [PostgreSQL's serialization guidance](https://www.postgresql.org/docs/current/mvcc-serialization-failure-handling.html) is a behavior reference, not copied implementation or an RRFlow compatibility claim.

The C-07 driver accepts this exact closed structured response as its existing `storage-runtime-conflict` diagnostic label and bounded numeric trace; it preserves the legacy error grammar for other conflicts and does not copy dynamic server text or keys. Malformed numbers, non-advancing cursors and extra fields cannot produce the structured label or trace. Failure accounting, attempt scheduling, budget limits, latency thresholds and abort/readback checks are unchanged. The real installed oracle now checks the returned details, diagnostic classification and hashed-key trace, repeats the same stale commit and observes another denial, explicitly aborts, verifies the rejected effect absent, performs a fresh transaction, restarts and verifies its idempotent receipt replay. It exercises a controlled schedule, not the previous campaign's exact internal conflict origin.
